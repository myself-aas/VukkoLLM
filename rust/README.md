# Rust crates

Phase 8 of [MIGRATION_PLAN.md](../MIGRATION_PLAN.md): how these crates are built
and packaged into the app.

```text
rust/
├── Cargo.toml          workspace: vukko-core, vukko-db, vukko-bridge
├── Cargo.lock          committed after the first CI run (see below)
├── rust-toolchain.toml pinned toolchain (CI reads RUST_VERSION too)
└── crates/
    ├── vukko-core/     domain, repositories, services, providers
    ├── vukko-db/       schema, migrations, integrity
    └── vukko-bridge/   FFI surface (the only crate that knows about the host)
```

## Pinning

| Tool | Version | Where |
|---|---|---|
| Rust | 1.89.0 | `rust/rust-toolchain.toml`, `RUST_VERSION` in `.github/workflows/rust.yml` |
| Node | see `.nvmrc` | CI reads it with `setup-node` |
| React Native | 0.81.4 | `package.json` (exact, no caret) |
| cargo-ndk | 3.x | installed by the Android build step below |
| NDK | 26.1.10909125 (`ANDROID_NDK_HOME`) | CI `android` workflow |

Do not float these: a Rust or NDK bump changes the shipped `.so`, and the
Kotlin/Rust ABI is only stable within a pinned toolchain.

`Cargo.lock` is not in this tree yet because it is generated by cargo, which the
authoring environment does not have. The `rust` workflow commits it on its first
run (`cargo generate-lockfile`) and asserts it is unchanged from then on; until
that run exists, dependency resolution is whatever `Cargo.toml`'s workspace
versions allow.

## Android (`cargo-ndk`)

Targets: `aarch64-linux-android` (arm64-v8a), `armv7-linux-androideabi`
(armeabi-v7a, only if a store still requires 32-bit), and `x86_64-linux-android`
for emulators. The library is packaged into
`android/app/src/main/jniLibs/<abi>/libvukko_bridge.so`.

Once the React Native host lands (`android/` per Step 1.2 of the plan) the
output directory below becomes real; this repository currently ships only the
existing Kotlin Android module in `app/`, so the `android` workflow stays red
until the host exists — deliberately, rather than being marked
`continue-on-error` and hiding the gap.

```bash
rustup target add aarch64-linux-android armv7-linux-androideabi x86_64-linux-android
cargo install cargo-ndk --version '^3'
export ANDROID_NDK_HOME="$ANDROID_SDK_ROOT/ndk/26.1.10909125"

cargo ndk -t arm64-v8a -t x86_64 -o android/app/src/main/jniLibs \
  build -p vukko-bridge --release
```

Debug builds use the `dev` profile (unoptimised, symbols kept); release uses the
workspace's `release` profile (`lto = true`, `codegen-units = 1`, `strip =
"symbols"`) and `release-with-debug` when symbols are needed for crash triage.
Symbols for shipped builds are uploaded to the crash backend, not into the APK.

## iOS

Targets: `aarch64-apple-ios` (device) and `aarch64-apple-ios-sim` (Apple
Silicon simulator); `x86_64-apple-ios` only if an Intel simulator is still
supported. The two static libraries are combined into an XCFramework:

```bash
cargo build -p vukko-bridge --release --target aarch64-apple-ios
cargo build -p vukko-bridge --release --target aarch64-apple-ios-sim
xcodebuild -create-xcframework \
  -library target/aarch64-apple-ios/release/libvukko_bridge.a \
  -library target/aarch64-apple-ios-sim/release/libvukko_bridge.a \
  -output VukkoBridge.xcframework
```

The XCFramework is added to the Xcode project's *Link Binary With Libraries*
phase, and its build step runs before *Compile Sources* so a clean checkout
builds without a manual `cargo` call.

## Bridge code generation (Step 8.3)

`src/types/native.ts` is the single source of truth for the bridge contract, and
`src/native/specs/` holds the TurboModule spec generated from it. Generated
files are not committed: `npm run codegen` writes them, and CI runs the same
command and fails on a dirty tree, so a stale generated file cannot be merged.

## What this repository can and cannot prove

The sandbox that produced these crates has no `cargo`. `tests/tooling/rustSyntax`
parses every `.rs` file with tree-sitter (syntax only), and `docs/RUST_VERIFICATION.md`
records exactly what is verified where. The first `cargo` run happens in CI, and
no cargo step is `continue-on-error`, so it is a real gate rather than a report.
